# Explainer Log — P1 — Platform, API & Release Engineer

One entry per merged story. Three things: **what it does**, **why it exists**,
**what could go wrong**. This is the artifact behind the Definition of Done item
"the owner can explain it out loud".

Written from the commits actually merged, not from the plan. If an entry cannot
be delivered verbally without opening the code, it is not finished.

Module-level detail lives in `docs/design/`; this log is the per-change record.


## 26 Oct — Phase 0 doc set

- **What it does:** Initiation document, research plan, preliminary architecture, 10-epic backlog, and the four-person ownership matrix.
- **Why it exists:** Four people needed to start in parallel on day one. The ownership matrix and the golden-fixture protocol are what made that possible without anyone blocking.
- **What could go wrong:** The nine-sprint plan in the backlog is not what happened; the real execution was one compressed week. ADR-006 says so explicitly, and the sprint reports must too.

## 28 Oct — SRS v1.0

- **What it does:** 63 functional, 15 non-functional and 8 security requirements, each FR naming the test that proves it.
- **Why it exists:** An FR with no test is not a requirement, it is an intention. Naming the test up front is what let the test report list the 7 that are still unmet instead of quietly dropping them.
- **What could go wrong:** NFR targets are numbers nobody has measured yet. Quoting one as a result would be the exact failure this project detects.

## 29 Oct — Architecture v1.0

- **What it does:** C4 context/container/component, an analysis sequence diagram and an ER diagram, all in Mermaid in version control.
- **Why it exists:** A diagram in a binary image file is how architecture docs become fiction. Mermaid diffs, so drift is visible in review.
- **What could go wrong:** The diagrams still have to be *read* against the code. §6.2's status rule was updated twice after the implementation disagreed with it.

## 30 Oct — Shared contracts v1

- **What it does:** 17 frozen Pydantic models with invariants enforced in the models: abstention consistency, the citation requirement, and `calibrated` defaulting to False.
- **Why it exists:** They are the only thing the four modules share. Putting invariants in the type means no stage can construct an inconsistent object, rather than every stage having to remember not to.
- **What could go wrong:** A contract change costs three people a rebase. Deliberately expensive, which also means a genuinely needed field is painful to add late.

## 30 Oct — Config, logging, errors

- **What it does:** One typed settings object, JSON logging with a redaction filter, and one exception class per API error.
- **Why it exists:** Startup refuses to serve an authenticated API with no keys, rather than defaulting to open. Redaction is a filter because a call-site convention gets broken by the next person.
- **What could go wrong:** `config_hash` deliberately ignores log level and auth. If something that *can* change a result is ever added outside its scope, runs become silently irreproducible.

## 30 Oct — ORM models and first migration

- **What it does:** Seven tables, JSONB on Postgres and JSON on SQLite via a type variant, with the first Alembic revision.
- **Why it exists:** A clone has to run with no services or nobody installs it. Foreign keys are switched on explicitly for SQLite, or the CASCADE rules silently do not apply in development.
- **What could go wrong:** Tests run on SQLite, so a Postgres-only behaviour could pass CI and fail in compose. The autogenerated migration also needed a hand-added `Text` import — generated code is not reviewed code.

## 30 Oct — CI pipeline

- **What it does:** Eight jobs: format, lint, strict types, tests with a 70% gate, migrations up *and* down, bandit, pip-audit, gitleaks, Trivy, and a container healthcheck.
- **Why it exists:** A job that cannot fail is not a check. No `continue-on-error` anywhere, and the model-backed tests are a separate job whose deselection is recorded rather than hidden.
- **What could go wrong:** It took three fixes to go green, and all three were real: a non-existent action tag, three vulnerable transitive dependencies, and pip's vendored SBOM. A pipeline that passes on the first try usually is not checking much.

## 02 Nov — Repository layer

- **What it does:** Contract-to-ORM mapping in one module, with per-claim writes.
- **Why it exists:** One place knows about both Pydantic and the ORM, so neither leaks into the other. Per-claim writes mean a crash loses one claim and `/results` returns finished work.
- **What could go wrong:** More transactions per run, traded deliberately for durability. `create_run` had to become idempotent after the route and the pipeline both inserted the same row and the background task died on a UNIQUE violation.

## 02 Nov — Orchestrator

- **What it does:** Runs the stages in order, isolates per-claim failures, and records provenance.
- **Why it exists:** Provenance records the backends that *actually ran*. A transformer model that fails to load falls back silently, and `lexical-fallback` in the record is the only way to tell a degraded result from a normal one.
- **What could go wrong:** A background task killed by a restart is not retried; a startup sweep marks it failed after 30 minutes. That is a mitigation, not a fix.

## 02 Nov — API v1

- **What it does:** Six required endpoints plus health, export and sources; API-key auth, rate limiting, one error handler.
- **Why it exists:** `202` + poll because a document is tens of seconds of work. Schemas separate from contracts so internal refactors are not breaking API changes. One error handler so no endpoint can leak a traceback.
- **What could go wrong:** Rate limiting is per-process, so several workers multiply the limit. No ASGI-level body cap, so a huge payload is parsed before being rejected.

## 02 Nov — API and integration suites

- **What it does:** 28 API tests and 12 integration tests, including a simulated mid-run stage failure.
- **Why it exists:** Integration tests check what unit tests structurally cannot: that the contracts line up and that failure isolation actually works.
- **What could go wrong:** The `:memory:` database wasted an hour — each SQLite connection gets its own, and the app's lifespan re-initialises the engine, so fixture tables were invisible.

## 02 Nov — Structured logging fix (EA-11)

- **What it does:** Subclassed the logger adapter so call-site `extra` merges with adapter context instead of being replaced.
- **Why it exists:** Every structured field in the codebase was being discarded, and the redaction filter had nothing to redact. The filter's own unit test passed because it built a LogRecord by hand.
- **What could go wrong:** The lesson is about the test, not the bug: a test that constructs its subject by hand verifies the function, not the system.

## 03 Nov — Container hardening

- **What it does:** Removed pip, setuptools and wheel from both the venv and the base image's system Python after installation.
- **Why it exists:** Trivy's 5 HIGH findings were pip's own vendored urllib3/msgpack/setuptools, declared in a bundled CycloneDX SBOM. Upgrading our dependencies could not clear them because they were not ours.
- **What could go wrong:** Nothing can be installed in the running container — intended, and it would surprise anyone expecting to `pip install` inside it for debugging.
